# B2-1 발표용 설명: 나만의 용돈 기입장

## 1. 프로젝트 소개

Python 3.10 이상과 표준 라이브러리만으로 만든 콘솔 가계부입니다. 거래 추가·조회·검색·수정·삭제, 월별 요약, 예산 관리, 카테고리 관리, CSV 가져오기·내보내기를 지원합니다. 프로그램을 종료해도 `data/`의 JSONL 파일 3개에 기록이 남습니다.

**발표 한 문장:** “사용자 명령을 처리하는 CLI와 거래 규칙, 파일 저장을 분리하고, 큰 파일도 줄 단위로 처리하도록 만든 용돈 기입장입니다.”

## 먼저 이해할 전체 흐름

```text
터미널 명령
  → __main__.py: main() 실행
  → cli.py: argparse로 명령/옵션 분석, input()으로 대화형 값 받기
  → service.py: 업무 규칙 검사와 계산
  → models.py: 거래 데이터와 값 검증
  → storage.py: JSONL 파일 읽기/쓰기
  → cli.py: 결과 또는 오류 메시지 출력
```

핵심은 **입력, 업무 규칙, 저장을 따로 구현한 것**입니다. 예를 들어 저장 형식을 바꾸더라도 CLI의 안내 문구를 고칠 필요가 없고, 출력 문구를 바꿔도 거래 금액 검증 코드를 수정할 필요가 없습니다.

## 2. 실행 시연 순서

`B2-1` 폴더에서 다음 순서로 시연합니다. `add` 입력에서는 날짜 `2024-01-15`, 타입 `expense`, 카테고리 `food`, 금액 `15000`, 메모 `점심`, 태그 `meal`을 입력합니다. 출력된 ID를 마지막 수정·삭제 명령에 사용합니다.

```bash
python3 -m budget_app category list
python3 -m budget_app add
python3 -m budget_app list --limit 5
python3 -m budget_app search --category food --tag meal
python3 -m budget_app budget set --month 2024-01 --amount 10000
python3 -m budget_app summary --month 2024-01 --top 3
python3 -m budget_app export --out demo.csv --month 2024-01
python3 -m budget_app update --id <출력된-ID> --amount 9000
python3 -m budget_app delete --id <출력된-ID>
```

위 예산 10,000원에 지출 15,000원을 넣으면 요약에서 **사용률 150.0%**와 초과 경고가 나옵니다. `import` 시연에는 README의 CSV 예제를 `sample.csv`로 저장한 뒤 `python3 -m budget_app import --from sample.csv`를 실행하면 됩니다.

## 4. 기능을 실제로 구현한 순서와 코드 흐름

### 4-1. 모델과 검증부터 만들었습니다

`models.py`의 `Transaction`은 거래 한 건을 표현합니다. 필드는 `id`, `date`, `type`, `category`, `amount`, `memo`, `tags`입니다. `@dataclass(frozen=True)`라서 만들어진 거래 객체의 필드를 실수로 직접 바꾸기 어렵습니다. 수정할 때는 기존 객체를 바꾸는 대신 새 `Transaction`을 만듭니다.

`valid_date()`는 `YYYY-MM-DD` 형태이면서 실제 존재하는 날짜인지 확인합니다. `positive_amount()`는 금액이 0보다 큰 정수인지 확인합니다. `Transaction.__post_init__()`는 타입이 `income` 또는 `expense`인지, 카테고리와 태그의 형태가 올바른지도 확인합니다. 등록된 카테고리인지 여부는 카테고리 파일을 알아야 하므로 `BudgetService._transaction()`에서 검사합니다.

### 4-2. 파일 저장소를 만들었습니다

`LedgerStore`를 생성하면 `data/` 폴더와 거래·카테고리·예산 JSONL 파일을 준비합니다. 카테고리 파일이 처음에는 비어 있으므로 `food`, `transport`, `rent`, `salary`, `other`를 자동 등록합니다.

```text
data/
├── transactions.jsonl  # 거래 한 건당 JSON 한 줄
├── categories.jsonl    # 카테고리 한 개당 JSON 한 줄
└── budgets.jsonl       # 월 예산 한 개당 JSON 한 줄
```

`data/`를 `.gitignore`에 넣어 개인 사용 기록은 GitHub에 올리지 않았습니다. `--data-dir` 옵션을 사용하면 저장 폴더를 바꿀 수 있습니다. 예: `python3 -m budget_app --data-dir ./my-data list`.

### 4-3. 거래 추가·조회·검색을 연결했습니다

`add`는 `cli.py`에서 `input()`으로 날짜부터 태그까지 순서대로 받은 다음 `BudgetService.add()`에 전달합니다. 서비스가 값과 등록 카테고리를 검사하고 UUID를 바탕으로 `TX-...` ID를 만든 후, `LedgerStore.append()`가 `transactions.jsonl` 끝에 한 줄을 추가합니다. 성공하면 CLI가 생성된 ID를 출력합니다.

`list`는 `service.list()`가 파일의 거래를 최신 날짜순으로 받아 `--limit` 개수만 출력합니다. `search`는 파일을 한 건씩 읽으면서 `--from`, `--to`, `--category`, `--type`, `--q`, `--tag` 조건을 모두 만족하는 거래만 남깁니다. 메모 검색은 대소문자를 구분하지 않고, 태그는 정확히 일치하는 값을 찾습니다. 검색 결과도 최신 날짜순으로 출력합니다.

### 4-4. 수정·삭제를 안전하게 구현했습니다

`update`는 **옵션 방식**입니다. 예를 들어 `update --id TX-... --amount 9000`을 입력하면 `BudgetService.update()`가 기존 거래의 다른 필드는 유지하고 금액만 바꾼 새 `Transaction`을 만듭니다. 새 값은 다시 검증합니다. `delete --id TX-...`는 대상 거래를 새 파일에서 제외합니다.

두 명령 모두 `LedgerStore.rewrite()`를 사용합니다. 저장소는 기존 파일을 한 줄씩 읽으며 임시 파일에 새 내용을 씁니다. 끝까지 기록하고 `fsync()`한 뒤 `os.replace()`로 원본과 교체합니다. 오류가 나면 교체하지 않고 임시 파일을 지웁니다. 대상 ID가 없으면 `False`를 반환하고 CLI가 “거래가 없습니다”라고 안내합니다.

### 4-5. 월별 요약과 예산을 만들었습니다

`summary --month YYYY-MM`은 거래를 한 번 순회하면서 그 달의 수입 합계, 지출 합계, 카테고리별 지출 합계를 누적합니다. 잔액은 `수입 - 지출`이고, 카테고리 지출을 큰 금액순으로 정렬해 `--top N`개만 출력합니다. 거래가 없는 달에는 “데이터 없음”을 표시합니다.

`budget set`은 월 예산을 `budgets.jsonl`에 저장합니다. 예산이 설정된 달의 요약에서는 `지출 ÷ 예산 × 100`으로 사용률을 계산하고, 지출이 예산보다 클 때 경고를 출력합니다. `budget show`로 저장된 예산만 따로 조회할 수도 있습니다.

### 4-6. 카테고리와 CSV를 만들었습니다

`category add/list/remove`는 등록 목록을 관리합니다. 삭제 전에 모든 거래를 순회하여 해당 카테고리를 사용 중인지 확인합니다. 사용 중이면 삭제를 거절해 기존 거래가 등록되지 않은 카테고리를 가리키는 상황을 막습니다.

`import --from file.csv`는 헤더와 각 행의 날짜·타입·카테고리·금액을 검사합니다. 모든 행을 임시 파일에 준비할 때까지 원본 거래 파일은 바뀌지 않습니다. 한 행이라도 틀리면 행 번호와 이유를 알리고 전체 가져오기를 취소합니다. 정상이라면 기존 거래와 새 거래를 합친 파일로 교체합니다. `export --out file.csv --month YYYY-MM`은 조건에 맞는 거래를 헤더 포함 UTF-8 CSV로 기록합니다. 두 명령 모두 `date,type,category,amount,memo,tags` 스키마를 사용합니다.

## 5. 제너레이터와 스트리밍을 설명하는 방법

`LedgerStore.transactions()`는 파일을 열고 한 줄을 JSON으로 변환할 때마다 `yield Transaction.from_dict(...)`를 실행합니다. 따라서 파일 전체를 `read()`나 `list()`로 메모리에 올리지 않습니다. `summary`도 이 반복자를 한 번 순회하며 합계만 유지합니다.

`list`와 `search`는 날짜 최신순이 필요합니다. 단순히 모든 거래를 메모리에 넣고 정렬하면 대용량 파일에서 메모리가 커집니다. 그래서 `newest_first()`는 최대 1,000건씩만 정렬해 임시 파일로 쓰고, `heapq.merge()`로 정렬된 묶음을 합쳐 한 건씩 `yield`합니다. **메모리 사용은 전체 거래 수가 아닌 묶음 크기와 묶음 개수에 좌우됩니다.**

**발표 문장:** “`yield`는 다음 거래가 필요할 때만 한 줄을 읽습니다. 최신순 정렬도 작은 묶음으로 나눠 처리해 파일이 커져도 전체 거래를 RAM에 담지 않습니다.”

## 6. 데이터 안전성을 설명하는 방법

수정·삭제는 기존 파일을 바로 덮어쓰지 않습니다. 같은 폴더에 임시 파일을 만들고 새 내용을 끝까지 기록한 뒤 `os.replace()`로 교체합니다. 입력 검증이나 쓰기 중 오류가 나면 임시 파일만 제거하고 원래 파일을 유지합니다. CSV 가져오기도 먼저 각 행의 날짜, 타입, 카테고리, 양수 금액을 확인해 임시 파일에 준비한 다음 반영합니다. 카테고리·예산 파일 갱신에도 같은 교체 방식을 사용합니다.

**발표 문장:** “잘못된 수정값이나 CSV 한 행의 오류 때문에 기존 거래 파일이 반쯤 바뀌지 않도록, 완성된 파일만 교체합니다.”

## 7. 데코레이터와 타입 힌트를 설명하는 방법

`@timed`는 `main()` 앞뒤의 시간 측정을 감싸는 데코레이터입니다. CLI 명령 코드마다 측정 코드를 복사하지 않아도 되고, `BUDGET_APP_TIMING=1`로 필요할 때만 결과를 확인할 수 있습니다. 타입 힌트 예시로 `BudgetService.summary(self, month: str, top: int) -> Summary`는 입력이 월 문자열과 개수이며 출력이 `Summary` 객체임을 보여 줍니다. `LedgerStore.transactions() -> Iterator[Transaction]`은 결과를 한 건씩 생성한다는 계약을 드러냅니다. 타입 힌트 자체가 런타임 검증을 대신하지는 않으므로 실제 값 검증 함수도 별도로 구현했습니다.

## 8. 2분 발표 대본

> 제가 만든 것은 파일 기반 용돈 기입장입니다. 거래를 추가·수정·삭제할 수 있고, 날짜나 카테고리로 검색할 수 있습니다. 월별 수입과 지출을 계산하고 예산 초과도 알려 줍니다. CSV로 내보내거나 가져올 수도 있습니다.
>
> 구조는 네 부분으로 나눴습니다. CLI는 사용자의 명령과 입력을 받고, 서비스는 가계부 규칙을 처리하며, 모델은 거래 데이터와 값 검증을 담당합니다. 저장소는 JSONL 파일 세 개에 거래, 카테고리, 예산을 각각 기록합니다.
>
> 큰 거래 파일도 처리할 수 있도록 `yield` 제너레이터로 한 줄씩 읽습니다. 날짜 최신순 목록은 1,000건씩 정렬해 임시 파일에 담고 병합하기 때문에 거래 전체를 한꺼번에 메모리에 올리지 않습니다.
>
> 수정이나 삭제를 할 때는 기존 파일을 직접 덮어쓰지 않습니다. 새 임시 파일을 끝까지 만든 뒤 교체합니다. CSV 가져오기도 모든 행을 검증한 후에만 반영합니다. 그래서 잘못된 입력이 들어와도 기존 기록을 보호합니다.
>
> 마지막으로 실행 시간 측정은 데코레이터로 분리했고, 타입 힌트로 함수의 입력과 출력 형태를 표시했습니다. 자동 테스트로 핵심 기능과 오류 상황을 확인했습니다.

## 9. 질문 대비

**왜 JSONL을 선택했나요?** 한 줄에 거래 하나를 저장하므로 거래를 순차적으로 읽고 새 거래를 끝에 붙이기 쉽습니다. CSV는 사용자와 데이터를 주고받는 형식으로만 사용했습니다.

**왜 ID가 필요한가요?** 날짜·금액이 같은 거래도 구별하고, 수정·삭제 대상을 정확히 지정하기 위해서입니다. UUID 기반 ID를 새 거래마다 부여합니다.

**없는 ID나 잘못된 입력은 어떻게 처리하나요?** 사용자에게 원인과 확인 방법을 보여 주고 오류 종료 코드 1을 반환합니다. 테스트에서 스택트레이스가 출력되지 않는 것도 확인합니다.

**카테고리를 지우면 기존 거래는 어떻게 되나요?** 사용 중인 카테고리는 삭제를 막습니다. 해당 거래의 카테고리를 먼저 변경하거나 거래를 삭제해야 합니다.

**같은 CSV를 두 번 가져오면 어떻게 되나요?** 매번 새 ID를 부여하므로 거래가 두 번 추가됩니다. 중복 제거는 이번 과제 범위 밖이며, 사용자에게 README에 이 동작을 명시했습니다.
