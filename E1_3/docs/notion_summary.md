# E1_3 미션 정리 — Mini NPU Simulator, 팀원에게 설명하기용

> 목적: 이 문서는 제출용 README와 달리, "내가 만든 걸 팀원에게 말로 설명할 수 있게" 개념 위주로 풀어쓴 노트입니다.

## 1. 이 미션이 뭘 하는 건지 한 줄로

**"컴퓨터가 숫자 배열 두 개를 비교해서 얼마나 비슷한지 점수를 매기는 방법(MAC 연산)을, AI 칩(NPU)이 하는 방식 그대로 흉내 내보는 것"**입니다. 십자가(+) 모양과 X 모양을 숫자로 표현하고, "이 패턴이 십자가에 가까운가 X에 가까운가"를 계산으로 판별하는 미니 프로그램을 만들었습니다.

## 2. 왜 MAC 연산이 AI의 핵심인가

사람은 그림을 보면 바로 "이건 십자가, 이건 X"라고 압니다. 그런데 컴퓨터는 눈이 없고 숫자만 압니다. 그래서:

1. 그림을 0/1(또는 실수) 숫자로 이루어진 2차원 배열로 바꾸고,
2. "십자가는 이런 숫자 패턴이다"라는 기준 배열(**필터**)을 미리 만들어두고,
3. 입력 패턴과 필터를 **같은 위치끼리 곱해서 다 더한다** → 이게 **MAC(Multiply-Accumulate, 곱하고 누적해서 더하기)**입니다.

곱해서 더한 값(점수)이 클수록 "그 필터 모양과 비슷하다"는 뜻입니다. 우리 프로그램에서는 Cross 필터로 낸 점수와 X 필터로 낸 점수를 비교해서, 점수가 더 높은 쪽으로 판정합니다.

실제 AI(딥러닝의 CNN 등)도 원리는 똑같습니다. 다만 필터가 3×3이 아니라 수백×수백 크기고, 그런 필터가 수천 개씩 있어서 MAC 연산을 이미지 한 장당 수억 번씩 해야 합니다. CPU는 이런 단순 반복을 하나씩 순서대로 처리하는 데는 강하지만, 이 정도 규모의 "곱하고 더하기"를 동시에 수천 개씩 처리하기엔 비효율적이라서, MAC 연산을 병렬로 왕창 처리하도록 특화된 칩인 **NPU**가 만들어졌습니다. 이번 미션은 그 NPU가 하는 일의 가장 작은 단위(MAC 한 번, 그리고 그게 크기별로 얼마나 오래 걸리는지)를 직접 코드로 재현해본 것입니다.

## 3. 프로그램이 실제로 하는 일 (모드별)

- **모드 1 (3×3 직접 입력)**: 필터 A, 필터 B, 패턴을 직접 타이핑해서 넣으면, 패턴이 A에 가까운지 B에 가까운지 점수로 비교해줍니다. "십자가 필터 vs X 필터에 X 패턴을 넣으면 X 필터 점수가 더 높다"를 직접 확인할 수 있는 모드예요.
- **모드 2 (`data.json` 분석)**: 미리 준비된 5×5, 13×13, 25×25 크기의 필터/패턴 데이터를 한꺼번에 읽어서, 각 패턴이 Cross인지 X인지 자동으로 판정하고, 원래 정답(`expected`)과 맞는지(PASS/FAIL) 채점까지 해줍니다.

## 4. "라벨 정규화"가 왜 필요했나

`data.json` 안에는 같은 개념이 여러 다른 표기로 섞여 있어요. 예를 들어 정답값(`expected`)은 `"+"`나 `"x"`로, 필터 이름은 `"cross"`나 `"x"`로 적혀 있습니다. 이걸 그대로 비교하면 `"+"`랑 `"cross"`가 같은 뜻인데도 문자열이 달라서 프로그램이 "다르다"고 착각할 수 있어요. 그래서 프로그램 안에서는 무조건 `Cross` / `X` 이 두 가지 **표준 이름**으로 통일(정규화)한 다음에만 비교하도록 만들었습니다. 데이터를 만든 사람이 표기를 어떻게 하든, 프로그램 내부 로직은 항상 같은 기준으로 판단하게 하려는 거예요.

## 5. 왜 점수를 `==`로 비교하면 안 되고 "허용오차(epsilon)"가 필요한가

컴퓨터의 실수(float)는 사람이 쓰는 10진수 소수를 완벽하게 표현하지 못하고, 아주 작은 오차를 가진 이진수로 근사해서 저장합니다. 그래서 수학적으로는 정확히 같은 값이라도, **더하는 순서나 방식이 다르면** 컴퓨터 안에서는 미묘하게 다른 값으로 계산될 수 있어요. 실제로 이번 `data.json`에는 일부러 이런 상황을 만들어 둔 케이스가 있었습니다 — Cross 점수와 X 점수가 이론상 정확히 같아야 하는데, 계산 과정에서 `0.9`와 `0.8999999999999999`처럼 소수점 한참 뒤에서 미세하게 달라졌어요. 이럴 때 `score_a == score_b`로 비교하면 "같아야 하는데 다르다"고 잘못 판단해서, 반올림이 어느 쪽으로 튀었느냐에 따라 우연히 정답을 맞히거나 틀리게 됩니다. 그래서 "두 값의 차이가 매우 작으면(`1e-9` 미만) 사실상 동점으로 보고 '판정 불가(UNDECIDED)'로 처리한다"는 **허용오차 기반 비교 정책**을 넣었습니다. 실제로 이 프로그램에서는 동점으로 판정된 케이스는 채점 규칙상 무조건 FAIL로 처리하도록 정했습니다(정답을 맞혔는지와 무관하게, "애매한 상황이었다"는 사실 자체를 기록에 남기는 셈).

## 6. 실행 결과가 말해주는 것

`data.json`을 돌려보면 6개 케이스 중 3개는 명확하게 판정돼서 PASS했고, 나머지 3개(`size_5_1`, `size_13_2`, `size_25_1`)는 정확히 위에서 설명한 부동소수점 동점 문제로 UNDECIDED → FAIL이 됐습니다. 이건 코드가 잘못돼서가 아니라, 데이터 자체가 "동점 처리 로직을 시험해보라"고 일부러 그렇게 설계된 것으로 보입니다. 즉 FAIL 3건은 전부 "수치 비교 문제" 카테고리이지, "라벨/스키마 문제"나 "로직 버그"가 아니라는 걸 구분해서 설명할 수 있어야 합니다.

## 7. 성능 표가 보여주는 O(N²)

크기가 3→5→13→25로 커질수록 연산 횟수(N²)와 평균 소요 시간이 함께 늘어나는 걸 표로 확인할 수 있습니다. MAC 연산은 N×N칸을 전부 한 번씩 곱하고 더해야 하니, 계산량이 딱 N²만큼 필요합니다(이중 for문 = 바깥 N번 × 안쪽 N번). 필터 한 변의 길이가 2배가 되면 계산량은 대략 4배가 되는 식이죠. 실제 AI 모델에서 필터 크기가 커지고 개수가 늘어나면 이 N²이 기하급수적으로 부담이 커지는데, 이게 바로 NPU 같은 전용 병렬 연산 칩이 필요한 이유와 직접 연결됩니다.

## 8. 코드로 보는 핵심 구현 (함수별 상세 설명)

여기부터는 `main.py`의 실제 코드를 그대로 가져와서, 왜 이렇게 짰는지 하나씩 설명합니다. 발표할 때 이 코드를 화면에 띄워놓고 아래 설명대로 말하면 됩니다.

### 8-1. 라벨 정규화 — `normalize_label`

```python
LABEL_MAP = {'+': 'Cross', 'cross': 'Cross', 'x': 'X'}

def normalize_label(raw):
    key = str(raw).strip().lower()
    if key not in LABEL_MAP:
        raise ValueError(f"알 수 없는 라벨: {raw}")
    return LABEL_MAP[key]
```

- 딕셔너리 하나(`LABEL_MAP`)에 "들어올 수 있는 표기 → 표준 이름"을 다 적어놓고, 함수는 그냥 `strip().lower()`로 소문자·공백 제거한 다음 딕셔너리에서 찾아주기만 합니다.
- 이 함수 하나로 `expected` 값(`'+'`/`'x'`)과 필터 키(`'cross'`/`'x'`) **정규화를 둘 다** 처리합니다 — 어차피 둘 다 "같은 뜻, 다른 표기"라는 같은 문제라서 함수를 나눌 필요가 없었습니다.
- 매핑에 없는 값이 들어오면(`'triangle'`처럼) 조용히 넘어가지 않고 `ValueError`를 던져서, 호출한 쪽(모드 2의 케이스 처리)이 "이 케이스는 처리 불가"로 잡아채게 만들었습니다.

### 8-2. MAC 연산 — `mac_score`

```python
def mac_score(pattern, filter_):
    total = 0.0
    for row_p, row_f in zip(pattern, filter_):
        for p, f in zip(row_p, row_f):
            total += p * f
    return total
```

- 이게 이 과제의 진짜 핵심입니다. `zip`으로 두 2차원 리스트를 같은 행끼리, 같은 칸끼리 짝지어서 **곱하고(Multiply) 누적해서 더하는(Accumulate)** 걸 그대로 코드로 옮긴 것뿐이에요.
- 바깥 `for`가 행(N번), 안쪽 `for`가 열(N번) 돌아서 총 N×N번 곱셈·덧셈이 일어납니다 — 이게 뒤에 나오는 "왜 O(N²)인가"의 근거입니다.
- NumPy의 `np.sum(pattern * filter_)` 같은 걸 쓰면 한 줄로 끝나지만, 과제 조건이 "외부 라이브러리 금지, 반복문으로 직접 구현"이라 순수 파이썬 반복문만 사용했습니다.

### 8-3. 판정 — `judge_label`

```python
EPSILON = 1e-9

def judge_label(score_cross, score_x, eps=EPSILON):
    if abs(score_cross - score_x) < eps:
        return 'UNDECIDED'
    return 'Cross' if score_cross > score_x else 'X'
```

- 두 점수의 차이의 절댓값이 `1e-9`보다 작으면 "사실상 같다"고 보고 `UNDECIDED`를 반환합니다. 이게 앞에서 설명한 "부동소수점이라 `==` 대신 허용오차로 비교해야 한다"는 원칙이 코드로 구현된 부분입니다.
- 동점이 아니면 그냥 점수 큰 쪽의 이름을 돌려줍니다. 모드 1에서는 이 `'Cross'`/`'X'`를 다시 `'A'`/`'B'`로 바꿔서 보여줍니다(필터 A가 Cross 역할, B가 X 역할이라는 뜻이 아니라, 그냥 사용자가 입력한 두 필터 중 어느 쪽 점수가 높은지를 표현하는 용도라서요).

### 8-4. 성능 측정 — `measure_avg_ms`

```python
def measure_avg_ms(func, *args, repeats=10):
    result = None
    total_seconds = 0.0
    for _ in range(repeats):
        start = time.perf_counter()
        result = func(*args)
        end = time.perf_counter()
        total_seconds += (end - start)
    avg_ms = (total_seconds / repeats) * 1000
    return result, avg_ms
```

- 아무 함수(`func`)나 인자(`*args`)와 함께 넘기면, 그 함수를 10번(`repeats`) 호출하면서 매번 `time.perf_counter()`로 걸린 시간을 재고 다 더한 다음 평균을 냅니다.
- 함수 하나로 모드 1(필터 A/B 점수 계산)과 모드 2(크기별 MAC 연산)의 성능 측정을 둘 다 처리합니다 — 측정 로직 자체는 "무슨 함수를 재는지"와 상관없어서 재사용이 가능했어요.
- `result`도 같이 돌려주는 이유는, 시간을 재는 김에 마지막 계산 결과도 그대로 활용하기 위해서입니다(모드 1에서 점수 출력할 때 다시 계산 안 해도 되게).

### 8-5. 패턴 생성기 — `generate_cross` / `generate_x` (보너스 겸용)

```python
def generate_cross(n):
    mid = n // 2
    return [[1.0 if (r == mid or c == mid) else 0.0 for c in range(n)] for r in range(n)]

def generate_x(n):
    return [[1.0 if (r == c or r + c == n - 1) else 0.0 for c in range(n)] for r in range(n)]
```

- `generate_cross(n)`: 가운데 행(`r == mid`)이나 가운데 열(`c == mid`)이면 1, 아니면 0 — 정확히 십자가 모양입니다.
- `generate_x(n)`: 왼쪽 위→오른쪽 아래 대각선(`r == c`)이거나 오른쪽 위→왼쪽 아래 대각선(`r + c == n - 1`)이면 1 — 정확히 X 모양입니다.
- 이 두 함수는 `data.json`에 없는 3×3 크기를 모드 2 성능 분석에서 벤치마크하려고 먼저 만든 건데, "크기 N을 넣으면 십자가/X를 자동 생성"하는 보너스 요구사항을 그대로 만족합니다.

### 8-6. 입력 검증 — `read_row` / `read_matrix`

```python
def read_row(n, label):
    while True:
        raw = input().split()
        if len(raw) != n:
            print(f"입력 형식 오류: 각 줄에 {n}개의 숫자를 공백으로 구분해 입력하세요.")
            continue
        try:
            return [float(x) for x in raw]
        except ValueError:
            print(f"입력 형식 오류: 각 줄에 {n}개의 숫자를 공백으로 구분해 입력하세요.")
```

- `while True`로 한 줄씩 계속 다시 물어보는 구조입니다. 실패 조건이 두 가지라 각각 체크합니다: ① 숫자 개수가 `n`개가 아님 → 바로 안내 후 재입력. ② 개수는 맞는데 `float()` 변환이 실패함(글자가 섞여 있는 경우) → 역시 안내 후 재입력.
- 성공하면(둘 다 통과하면) `return`으로 빠져나가서 다음 줄로 넘어갑니다. `read_matrix(n, label)`은 이 함수를 `n`번 호출해서 한 줄씩 쌓아 행렬을 완성합니다.

### 8-7. 스키마 방어 — 모드 2의 케이스 처리 루프

    try:

- 핵심은 **케이스 하나마다 통째로 `try/except`로 감싸놨다**는 점입니다. 정규식으로 `N`을 못 뽑거나, 그 크기의 필터가 없거나, 패턴 크기가 필터 크기와 다르면 그냥 `ValueError`를 던지고, 바깥의 `except`가 그걸 잡아서 "이 케이스는 FAIL, 사유는 이거"라고 기록한 뒤 **`for` 루프는 계속 다음 케이스로 넘어갑니다.**
- 그래서 데이터 8개 중 1개가 깨져 있어도 프로그램 전체가 죽지 않고, 나머지 7개는 정상적으로 판정됩니다 — 실제로 `size_13` 필터를 통째로 지우고 `size_25_1` 패턴을 24×25로 깨뜨린 가짜 데이터로 이 부분을 테스트해봤습니다.

### 8-8. 시뮬레이터 최적화(보너스) — `flatten` / `mac_score_1d`

```python
def flatten(matrix):
    flat = []
    for row in matrix:
        flat.extend(row)
    return flat


def mac_score_1d(pattern_flat, filter_flat, n):
    total = 0.0
    for idx in range(n * n):
        total += pattern_flat[idx] * filter_flat[idx]
    return total
```

- `flatten`은 `[[1,0],[0,1]]` 같은 2차원 리스트를 `[1,0,0,1]` 같은 1차원 리스트로 한 줄씩 이어붙입니다.
- `mac_score_1d`는 `mac_score`처럼 `zip`으로 행/열을 짝짓는 대신, `range(n * n)`으로 인덱스 하나만 늘려가며 두 1차원 리스트의 같은 위치를 곱해서 더합니다. 2차원이든 1차원이든 값 자체는 똑같이 저장돼 있고 "어떻게 접근하느냐"만 다른 거라, 계산 결과는 두 함수 다 완전히 동일합니다(직접 비교해서 확인함).
- 모드 2 성능 분석에서 같은 패턴/필터를 `flatten`으로 바꿔서 `mac_score`(2D)와 `mac_score_1d`(1D)를 각각 10회씩 재고 비교표를 출력합니다. 실측 결과 모든 크기에서 1D 쪽이 더 빨랐는데(1.2~2배), `zip`이 매 반복마다 튜플을 만들고 풀어내는 오버헤드가 있는 반면 정수 인덱스로 리스트에 바로 접근하는 쪽이 파이썬 입장에서 더 가벼운 연산이기 때문입니다.

## 9. 만든 순서 (팀원에게 "어떻게 만들었어?"라고 물어보면 이 순서로 답하면 됨)

1. 먼저 `data.json`을 열어서 구조부터 파악했어요 — 필터가 5/13/25 세 가지 크기로 있고, 정답 표기가 `'+'`/`'x'`, 필터 이름 표기가 `'cross'`/`'x'`로 서로 다르다는 걸 확인했습니다.
2. 그 다음 제일 핵심인 세 함수(라벨 정규화, MAC 점수 계산, epsilon 판정)부터 만들었어요. 나머지는 다 이 세 개를 조합하는 일이라서요.
3. 성능을 잴 때 쓸 도구(10회 평균 측정 함수)와, `data.json`에 없는 3×3 크기를 테스트하려고 십자가/X 패턴을 자동으로 만들어주는 함수를 준비했어요.
4. "3×3 직접 입력" 모드부터 먼저 완성해서, 미션 소개에 나온 예시(십자가 vs X 필터에 X 패턴)를 직접 입력해보고 점수가 문서에 나온 값이랑 똑같이 나오는지 확인했어요. 여기서 맞아야 이후 로직도 신뢰할 수 있으니까요.
5. 그 다음 "`data.json` 분석" 모드를 필터 로드 → 패턴 판정 → 성능 측정 → 결과 요약 순서로 하나씩 붙여나갔어요.
6. 일부러 필터를 하나 지우거나 패턴 크기를 깨뜨린 가짜 데이터를 만들어서 돌려보고, 프로그램이 죽지 않고 그 케이스만 실패 처리되는지 확인했어요. 실제 과제 데이터는 이렇게 깨져 있지 않지만, "혹시 깨져 있어도 안 죽어야 한다"는 요구사항이라 일부러 테스트했습니다.
7. 마지막으로 실제 `data.json`을 돌려서 나온 진짜 결과(몇 개 통과했는지, 왜 실패했는지)를 가지고 README와 이 문서를 썼어요. 추측이 아니라 실제로 실행해본 결과를 그대로 옮긴 거예요.
8. 처음엔 "1차원 배열 최적화" 보너스를 범위 밖으로 뒀는데, "그게 그렇게 어려운 것도 아닌데 왜 안 했냐"는 피드백을 받고 실제로 만들어봤어요. `flatten` + `mac_score_1d`를 추가하고, 기존 2D 버전과 같은 입력·같은 반복 횟수로 성능을 재서 비교표까지 붙였습니다.

## 10. 보너스 과제는 어디까지 했나

- **패턴 생성기(구현함)**: 크기 N만 주면 십자가/X 패턴을 자동으로 만들어주는 함수를 만들었어요. 사실 이건 보너스라서 만든 게 아니라, `data.json`에 없는 3×3 크기 성능 측정을 하려면 어차피 필요해서 만들었는데, 그게 그대로 보너스 요구사항(패턴 생성기)이 됐어요.
- **1차원 배열 최적화 비교(구현함)**: `flatten`으로 2차원 리스트를 1차원으로 펼치고, `mac_score_1d`가 정수 인덱스로 순차 접근하도록 만들었어요. 같은 입력·같은 반복 횟수(10회)로 기존 `mac_score`(2D)와 비교해보니, 3×3~25×25 전 구간에서 1D 버전이 1.2~2배 더 빨랐습니다. `zip`이 매번 튜플을 만들고 푸는 비용이 있는 반면, 1차원 배열을 정수 인덱스로 바로 접근하는 게 더 단순한 연산이기 때문이라고 설명하면 됩니다.
